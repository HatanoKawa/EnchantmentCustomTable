# 1.21.1 Fabric / NeoForge 实际 GUI 验证：第一轮

日期：2026-09-22，Asia/Shanghai。结论：可以由 Codex 独立执行本轮离散 GUI 回归，
已完成两端实测并发现真实物品状态问题；目前仍不能覆盖 Shift+鼠标路径，也不作为无人值守 CI 的证明。
本轮没有接入 Jev，没有修改或修复业务代码。

## 基准与方法

- 业务基准：`dev` 的 `46726cb`（`fix: consume books inserted into Fabric generated slots`）。
- 隔离目录：`EnchantmentCustomTable-gui-validation`，分支 `codex/macos-gui-validation`；
  窗口接入基于 `dd33bd2`。原始 `dev` 工作区保持原提交且无改动。
- Minecraft 1.21.1；模组 2.0.2；NeoForge 21.1.136；Fabric Loader 0.19.3、Fabric API 0.116.12+1.21.1。
- macOS 本机，Gradle JVM Java 25，实际游戏为 Java 21 toolchain。通过现有 `runClient`
  任务准备依赖、导出启动参数，由本地 `.app` 入口运行同一开发客户端。
- 专用创造超平坦存档：Fabric `ECT-Fabric-GUI-R1`，NeoForge `ECT-GUI-1211`。
  测试窗口 854×508 点，F2 原始截图 1708×960 像素；英文界面。
- 历史问题从当前 `.ai/` 中的测试、维护和设计记录提取，具体来源见
  [28 项用例](cases-1.21.1.md)。没有把历史 JVM 测试结果计入本轮 GUI 通过数。
- 数据包仅准备世界/背包、执行原版重载和读取服务端数据；放入、取出、搜索、翻页、导出、
  保存退出和重进都经真实游戏界面操作。以屏幕状态和 `GUIBLOCK` / `GUIPLAYER` 对照判断。
- 默认组费用为 36 绿宝石或 4 绿宝石块，四个布尔开关均为 false；配置组将四个开关同时设为 true。
  两端测试完成后均正常退出，配置已按字节比对恢复原文件。未测试所有开关排列组合。

## R1-01：普通兑换消耗在重进世界后回滚

影响：两端，建议优先级高。玩家保留已兑换的附魔书，同时重新获得已消耗材料，形成重复获益条件。

复现：默认配置执行 `ectguicboundary`，放入 2 本书与合计 36 绿宝石，搜索 sharpness 并普通领取
一本。确认台内为 1 书/0 绿宝石；保存退出到标题，重进同一世界，再打开台子及读取数据。
不要重新执行准备函数。

预期：仍为 1 书/0 绿宝石，玩家保留一本 Sharpness V。
实际：恢复为 2 书/36 绿宝石，玩家的 Sharpness V 仍在。普通关闭重开未触发回滚。

| 证据 | 兑换后 | 保存重载后 |
| --- | --- | --- |
| Fabric | 16:34:50 截图：1 书/0 绿宝石 | 16:37:03 原版 `data get block`：2 书/36 绿宝石；16:37:04 截图保留玩家结果 |
| NeoForge | 17:19:41.945 服务端：1 书；玩家 Sharpness V | 17:20:55.502 服务端：2 书/36 绿宝石；玩家 Sharpness V 不变 |

Fabric 的最早检查函数尚未输出数据，因此兑换前后并无完整配对 NBT；这里使用兑换后的截图加
重载后的原版命令。NeoForge 则有完整的前后服务端记录，两端结论分别有实际依据。

## R1-02：复制模式重进世界后材料槽显示为空

影响：两端，建议优先级中。GUI 与服务端状态不一致；本次没有发现材料实际丢失。

复现：默认配置执行 `ectguiccopy`，放入 3 本书、12 绿宝石块与 Sharpness V 模板。
初次自动生成扣一次费用，取走一本复制结果后自动补位再扣一次，确认台内剩 1 书/4 块，
模板与待取输出都为 Sharpness V。保存退出再进入，打开转换台。

预期：所有四个持久槽与退出前一致。实际：模板和输出可见，但书本与支付槽显示为空。
关闭异常界面后再次读取服务端数据，仍为 1 书/4 块，玩家所得也未变。

- Fabric：16:59:18 与 17:00:02 的 `GUIBLOCK` / `GUIPLAYER` 完全一致；
  中间 17:00:01 截图显示两个材料槽空。此前 16:42–16:43 也复现过。
- NeoForge：17:27:19.496 与 17:28:17.910 的记录一致；17:28:17 截图显示材料为空。

截图：[Fabric](evidence/round1-2026-09-22/fabric-copy-empty-inputs.png)、
[NeoForge](evidence/round1-2026-09-22/neoforge-copy-empty-inputs.png)。
需要排查客户端菜单初始化/同步；这只是排查方向，本轮未定位代码根因。

## R1-03：Fabric 普通拆书取出时丢失一级

影响：Fabric 1.21.1，建议优先级高；NeoForge 对照三轮正常。这是等级损失，不能仅以
“没有重复增级”判定历史 issue25 回归通过。

复现：默认配置执行 `ectguiesplit`，将 Looting III 附魔书放入主槽；普通单击候选中的
Looting I，放到空快捷栏。读取主槽及玩家数据，然后将该书放回候选槽，再读取。

| 时刻 / 加载器 | 台内源书 | 玩家取出书 |
| --- | --- | --- |
| Fabric 16:55:49，操作前 | Looting III | 无 |
| Fabric 16:56:26，单次取出后 | **Looting I** | Looting I |
| Fabric 16:56:58，放回后 | **Looting II** | 无 |
| NeoForge 17:23:00，操作前 | Looting III | 无 |
| NeoForge 17:23:02，取出后 | Looting II | Looting I |
| NeoForge 17:23:34 / 17:23:53 / 17:24:21，三轮放回后 | Looting III | 无 |

预期每轮 III → II + I → III。Fabric 在第一个受控循环即失败，未把其后续循环记为通过。
主要证据为下面保留的服务端日志行，不用后续场景的截图代替该循环证据。

## 可行性和未覆盖范围

本轮无需额外提供信息即可完成已支持的输入路径。已有可复用的启动入口、原版准备数据包、
逐项预期、双端结果和缺陷证据，能够用于修复后回归。整个流程仍由代理观察画面逐步推进，
没有实现一键运行并自动生成断言的测试执行器；中途暂停时间也不能作为模型效率基准。

当前 CUA 的 `click` 无修饰键参数，单独 `pressKey("Shift_L")` 返回
`keyPressIncludedNoNonModifierKeys`，所以 E02/E06 留为阻塞。完成这部分需要人工按用例操作，
或扩展输入驱动后再次验证；本轮没有模拟成功来填补覆盖。

普通拖动一本不可堆叠书只使其跟随光标，需下一次点击放下，因此也未覆盖 QUICK_CRAFT。
此外尚未覆盖多人、漏斗、满背包、破坏掉落、数字键交换、中文搜索、其他 GUI 缩放、
完整配置组合和其他 Minecraft 版本。现有失败项修复及 Shift 路径补测前，不应将这轮结果
视为完整 GUI 发布验收。

建议下一轮先修复 R1-01 与 R1-03，再修复 R1-02；重复本套用例，并补齐 Shift 两项。
发现于两端的症状并不能单独证明共享代码是根因，修复前仍需分别定位。
